# hermes-agent + DeepSeek в Docker-контейнере

Автоматизация развёртывания ИИ-ассистента на базе
[hermes-agent](https://hermes-agent.nousresearch.com/) в отдельном
Docker-контейнере, провайдер модели — DeepSeek.

## Почему скрипты, а не «уже развёрнуто»

Сессия, в которой это писалось, идёт в изолированном контейнере, привязанном
к репозиторию. Оттуда до сервера не дотянуться, и это проверено, а не
предположено:

| Нужно | Факт |
|---|---|
| `ssh` | бинарника нет в образе |
| TCP :22 на сервер | egress закрыт, соединение уходит в таймаут |
| `docker` | клиент есть, демона нет: `dial unix /var/run/docker.sock: no such file` |
| `hermes-agent.nousresearch.com` | `CONNECT tunnel failed, response 403` |
| `api.deepseek.com` | то же, 403 от прокси по сетевой политике |

Поэтому здесь лежит то, что закрывает задачу с вашей стороны: идемпотентный
набор шагов, который делает ровно то же самое, но с машины, у которой доступ
есть. Каждый шаг проверяет собственный результат и падает с реальным выводом
команды, а не идёт вслепую.

## Запуск

```bash
cd deploy/hermes-node
cp config.env.example config.env
$EDITOR config.env          # IP, ключ DeepSeek, номер ноды
./run-all.sh
```

Шаги можно гонять и по одному — они независимы и повторный запуск ничего не
ломает:

```bash
scripts/00-preflight.sh          # проверки до изменений: ключ, модель, доступы
scripts/01-host-setup.sh         # docker, entrypoint, контейнер
scripts/02-ssh-access.sh         # ключ, ~/.ssh/config, вход в контейнер
scripts/03-install-hermes.sh     # пакеты + установщик (с обходом 403)
scripts/04-configure-deepseek.sh # ключ, права, модель, base_url, плагин
scripts/05-gateway.sh            # автозапуск gateway
scripts/06-verify.sh             # живой запрос и разбор ответа
scripts/07-study-kit.sh          # опционально: персона и память
```

Порт SSH контейнера считается из номера ноды: `22<NN>`. Нода 18 → `2218`,
контейнер `node18`, хост-алиас `yc-node18`.

## Что исправлено против исходной инструкции

Инструкция в постановке задачи содержит ошибки, часть из которых гарантированно
ломает установку. Здесь они устранены.

**1. Ключ DeepSeek в шаге 4 испорчен.** Там написано
`export DEEPSEEK_API_KEY= 158.160.240.14_API` — в строку ключа попал IP-адрес,
плюс пробел после `=`. Даже с правильным ключом такая строка оставила бы
переменную пустой: `export X= sk-...` присваивает `X` пустое значение.
Скрипт пишет ровно `export DEEPSEEK_API_KEY=sk-...` без пробела и предварительно
вычищает старые вхождения, чтобы не появились дубли.

**2. Плейсхолдеры не заменены.** `ВАШ_IP` остался литералом по всему тексту,
а `НОМЕР_НОДЫ` местами превратился в `nodeНОМЕР 18` — с пробелом внутри пути
(`/srv/nodeНОМЕР 18/entrypoint.sh`, `ssh yc-nodeНОМЕР 18`). Все имена и пути
теперь выводятся из двух переменных в `config.env`.

**3. Запасной образ в инструкции нерабочий.** Предлагалось запустить голый
`ubuntu:24.04` с `--entrypoint node-entry.sh`, а sshd и пользователя `admin`
доставить внутрь потом. Так нельзя: entrypoint первой строкой зовёт
`/usr/sbin/sshd`, которого в чистом ubuntu нет, контейнер падает мгновенно, и
выполнять `docker exec` уже негде. Заменено на `Dockerfile.fallback` —
образ собирается заранее и запускается уже готовым.

**4. `usermod -aG docker vokdub`.** Пользователь `vokdub` в инструкции больше
нигде не упоминается. Скрипт добавляет в группу того, под кем реально идёт
подключение, и пропускает шаг для `root`.

**5. Порядок создания entrypoint.** Инструкция предупреждает об этом сноской,
но команда `docker run` идёт раньше. Если смонтировать несуществующий путь,
Docker создаст на его месте **каталог**, и контейнер не стартует. Скрипт
создаёт файл до `docker run` и убирает каталог, если он остался от прошлой
неудачной попытки.

**6. Модель `deepseek-v4-flash` не подтверждена.** Публичный API DeepSeek
отдаёт `deepseek-chat` и `deepseek-reasoner`. Проверить из этой сессии нельзя —
домен закрыт прокси. Поэтому `00-preflight.sh` делает живой `GET /models`,
печатает реальный список и **останавливается до любых изменений на сервере**,
если модели из `config.env` в нём нет. Название сохранено как есть — если
`deepseek-v4-flash` существует, preflight это подтвердит.

**7. Проверка результата.** Шаг 6 разбирает фактический ответ и разводит
случаи `OK` / 402 / 403 / Permission denied / несуществующая модель по разным
кодам выхода, а 403 и Permission denied ещё и чинит на месте.

## Безопасность ключа

Ключ, присланный в постановке задачи, прошёл открытым текстом через переписку.
**Считайте его скомпрометированным и выпустите новый** на
https://platform.deepseek.com/api_keys, старый отзовите.

В репозиторий ключ не попадает: `config.env` в `.gitignore`, в коде и истории
его нет — скрипты читают значение из вашего локального файла.

## Диагностика

| Симптом | Причина и что делать |
|---|---|
| `HTTP 402 Insufficient Balance` | Конфиг верный, на счету пусто. https://platform.deepseek.com/top_up |
| `HTTP 403 Access denied by security policy` | Слетел `model.base_url`, запрос ушёл в OpenRouter — тот режет серверные IP. `06-verify.sh` вернёт значение сам |
| `Permission denied` на `.env` | Владелец `~/.hermes`. `sudo chown -R admin:admin /home/admin/.hermes` |
| Установщик обрывается на распаковке | Нет `xz-utils` (tar.xz) или `unzip` (zip) |
| Установщик висит | Забыты `--skip-setup --skip-browser`, ждёт ответа в интерактивном мастере |
| `install.sh` отдаёт 403 | Vercel WAF режет часть серверных IP. Шаг 3 сам качает файл локально и заливает по scp |
| Контейнер не стартует | На месте `entrypoint.sh` каталог, либо в образе нет sshd. Смотри `docker logs <контейнер>` |
| `No messaging platforms enabled` в логе | Норма. Платформы не подключены, работает CLI |
