# Нативный слой

DLL, которая грузится в процесс игры и раздаёт игровые события активному
режиму. Всё, что нельзя сделать конфигом — состояние режима, счёт, выбор
персонажа, свой UI, — живёт здесь.

## Состояние

Собирается и работает вся часть, не зависящая от конкретного билда игры:
загрузка, лог, поиск по сигнатуре, установка и снятие перехвата, реестр
режимов. Не заполнено ровно одно — сигнатура `ProcessEvent`, снять её можно
только с реального экзешника.

Пока сигнатуры нет, слой грузится с `Enabled=0`: пишет в лог, что попал в
процесс, и в чужой код не лезет. Это рабочее состояние для проверки, что
загрузчик вообще подхватывает мод.

## Сборка

Игра 32-битная, поэтому и DLL обязана быть x86. CMake проверяет это и падает
с внятным сообщением, если конфигурация 64-битная.

**MSVC** (предпочтительно — игра собрана им):

```
cmake -A Win32 -B build
cmake --build build --config Release
```

**MinGW, в том числе кросс-сборкой из Linux:**

```
cmake -B build -DCMAKE_TOOLCHAIN_FILE=cmake/mingw-i686.cmake -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

На выходе `DishonoredModKit.asi`.

## Тесты

```
cmake -B build-tests tests && cmake --build build-tests && ./build-tests/test_bytepattern
```

Проверяются разбор сигнатур и кодирование относительного перехода — то, что
роняет игру мгновенно и без внятного стека. Тесты не трогают `windows.h` и
гоняются на любой машине.

## Установка

1. [Ultimate ASI Loader](https://github.com/ThirteenAG/Ultimate-ASI-Loader) —
   32-битную версию, переименованную в `d3d9.dll`, положить в
   `Dishonored\Binaries\Win32\` рядом с экзешником. Игра на DirectX 9, поэтому
   проксируется именно `d3d9.dll`.
2. Туда же `DishonoredModKit.asi` и `native.ini`.
3. Запустить игру, открыть `DishonoredModKit.log` рядом с DLL. Строка
   «нативный слой загружен» означает, что связка работает.

## Как снять сигнатуру ProcessEvent

Это единственный шаг, требующий реверса. Порядок примерно такой.

1. Открыть `Dishonored.exe` в дизассемблере (IDA, Ghidra, x64dbg).
2. Найти `ProcessEvent`. Самая надёжная зацепка — строки движка: UE3 при
   ошибках скрипта печатает сообщения, ссылающиеся на имя функции, и от них
   получается выйти на саму `ProcessEvent`. Второй путь — по вызовам из
   виртуальной таблицы `UObject`, у неё `ProcessEvent` на фиксированном
   индексе для всей ветки UE3.
3. Взять 12–20 байт от начала функции. Байты, содержащие абсолютные адреса
   (операнды `call`, `mov` с константой-адресом), замаскировать через `??` —
   именно они меняются от сборки к сборке.
4. Записать в `native.ini` как `Pattern=`.
5. Посмотреть в дизассемблере, где заканчивается инструкция, пересекающая
   пятый байт функции. Это и есть `PrologueBytes` — граница обязана попасть
   ровно на конец инструкции, иначе трамплин будет исполнять обрубок.
6. Поставить `Enabled=1`, запустить игру, посмотреть лог.

Слой сам защищается от двух самых частых ошибок: если сигнатура не найдена
или найдена больше одного раза, хук не ставится и в лог идёт причина.
Неоднозначная сигнатура опаснее ненайденной — она молча цепляет не ту функцию.

## Устройство

| Файл | Что делает |
|---|---|
| `dllmain.cpp` | точка входа, чтение `native.ini`, установка хука |
| `bytepattern.h` | разбор сигнатур и кодирование перехода, без `windows.h` |
| `sigscan.cpp` | поиск сигнатуры в памяти главного модуля |
| `detour.cpp` | перехват функции через JMP с трамплином |
| `mode.cpp` | реестр режимов, встроенный режим-наблюдатель |
| `ue3.h` | соглашение вызова `ProcessEvent`, привязки к билду |
| `log.cpp` | лог в файл рядом с DLL |

Работа в `DllMain` намеренно сведена к запуску потока: он вызывается под
блокировкой загрузчика, где нельзя ни грузить модули, ни ждать синхронизацию.
